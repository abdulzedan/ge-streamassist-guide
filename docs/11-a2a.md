# 11. A2A: registering agents and the native invocation surface

Two distinct things share the "A2A" name here:

1. **Registering an external A2A server as an agent** (so streamAssist can
   route to it) — admin, v1alpha, Preview.
2. **The native A2A invocation surface** — calling ANY registered agent
   directly over the A2A protocol, bypassing the orchestrator — v1, verified
   working.

## 1. Registering an A2A agent

```bash
POST {ASSISTANT}/agents
{
  "displayName": "Loan Compliance Supervisor",
  "description": "Audits equipment finance packages for compliance.",
  "a2aAgentDefinition": {
    "jsonAgentCard": "{ \"protocolVersion\": \"0.3\", \"name\": \"…\", \"description\": \"…\", \"url\": \"https://your-a2a-server…\", \"version\": \"1.0\", \"defaultInputModes\": [\"text\"], \"defaultOutputModes\": [\"text\"], \"capabilities\": {}, \"skills\": [...] }"
  },
  "authorizationConfig": { "agentAuthorization": "projects/…/authorizations/…" }
}
```

- `jsonAgentCard` is the agent card **as an escaped JSON string**.
- Gemini Enterprise speaks the **A2A v0.3 streaming mechanism**. If your
  server uses A2A SDK v1.0+, use the compat packages
  (Python `a2a.compat.v0_3`, Go `a2acompat/a2av0`).
- Traffic to A2A agents registered this way does **not** traverse Agent
  Gateway — gateway policies don't apply.
- A2A agents hosted on Agent Runtime need a `cloud-platform`-scoped
  authorization.

Once registered, the agent is invoked through streamAssist exactly like any
other (`agentsSpec` + agent ID — chapter 5).

## 2. Native A2A surface (direct line to a registered agent)

Every registered agent — ADK ones included — exposes an A2A endpoint under
the assistant. This is the way to **guarantee** which agent answers (no
orchestrator, no query classifier, no routing heuristics).

### Get the agent card ([snippet 23](../snippets/curl/23-a2a-get-card.sh))

```
GET https://{host}/v1/{ASSISTANT}/agents/{AGENT_ID}/a2a/v1/card
```

Returns name, description, `url` (the agent's A2A base), input/output modes,
`preferredTransport` (HTTP+JSON).

### Send a message ([snippet 24](../snippets/curl/24-a2a-message-stream.sh))

```
POST https://{host}/v1/{ASSISTANT}/agents/{AGENT_ID}/a2a/v1/message:stream
{
  "message": {
    "role": "ROLE_USER",
    "content": [ { "text": "Audit this loan package summary…" } ],
    "messageId": "msg-001"
  }
}
```

Verified response shape: a streamed JSON array whose items carry
`message.role: "ROLE_AGENT"`, `message.contextId` = a session resource name
(pass it back as `contextId` for multi-turn), and — Gemini Enterprise
specific — the familiar `answer.replies[]` structure embedded under
`message.metadata`, including `thought` fragments and per-reply `agent` IDs.

Sibling methods: `message:send` (non-streaming), `tasks:get / cancel /
subscribe`, `tasks.pushNotificationConfigs.*`.

### streamAssist vs native A2A

| | streamAssist + agentsSpec | native `a2a/v1/message:stream` |
|---|---|---|
| Orchestrator/planner | yes (may answer trivial queries itself) | no — the agent always gets the message |
| Sessions & files | full support | `contextId` continuity |
| Tools (grounding, media) | yes | agent's own tools only |
| Chit-chat classifier | yes (can SKIP) | no |
| API version | v1alpha for agentsSpec | v1 |

Use the native surface for deterministic agent-to-agent integrations and
automated pipelines; use streamAssist when you want the assistant experience.
